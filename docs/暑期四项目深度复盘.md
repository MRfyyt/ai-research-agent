## 三、每个项目的核心逻辑与技术决策

### Week 1 — CLI AI 助手：学会"调 API"

**核心链路：**
```
用户输入 → while True 循环
  → client.chat.completions.create(model="deepseek-v4-pro", messages=[...], stream=True)
  → 逐 chunk 打印（打字机效果）
```

**文件架构：**
```
main.py（交互循环）
  → chat.py（ChatSession 类，封装 API + 流式输出 + 重试）
    → config.py（Pydantic 校验，从 .env 读 DeepSeek 配置）
    → utils.py（@retry 装饰器、TokenCounter 上下文管理器、日志）
```

**工程技能 5 件套：**

| 技能 | 文件 | 代码 | 为什么需要 |
|------|------|------|-----------|
| 装饰器 | `utils.py` | `@retry(max_attempts=3)` | API 会超时，需要自动重试 |
| Pydantic | `config.py` | `class LLMConfig(BaseModel)` | 配置写错立即报错，不等到运行时才发现 |
| 上下文管理器 | `utils.py` | `with TokenCounter("流式")` | 进入计时、退出打印，自动管理资源 |
| 流式输出 | `chat.py` | `for chunk in stream: print(text, end="")` | 用户体验——不用等完整回复 |
| 日志 | `utils.py` | `logging.getLogger("ai-cli")` | 出错时知道第几步、什么原因 |

**技术决策：** 为什么用 OpenAI SDK 调 DeepSeek？→ DeepSeek API 兼容 OpenAI 格式，换 `base_url` 即可，不用学新 SDK。

### Week 2 — RAG 知识库问答：学会"喂知识"

**核心链路：**
```
上传 PDF → pypdf 提取文字 → split("\n") 切段
  → sentence-transformers 向量化（384 维）
  → ChromaDB 持久化存储
  → 用户提问 → 向量化 → 语义搜索 top_k=3
  → 搜索结果 + 问题 → 拼接 Prompt → DeepSeek 生成回答（带来源引用）
```

**技术决策链：**

| 决策 | 原因 |
|------|------|
| 为什么用本地 Embedding 模型？ | DeepSeek 不提供 Embedding API → 查 GitHub Issues 确认 → 用 sentence-transformers 本地跑 |
| 为什么选 ChromaDB？ | 轻量、Python 原生、一行安装、不需要 Docker |
| 为什么前端用 Streamlit？ | 纯 Python，不需要写 HTML/CSS/JS |
| HuggingFace 被墙怎么办？ | `os.environ["HF_ENDPOINT"] = "https://hf-mirror.com"` |

**复盘 Bug：** `ask()` 函数内部重复调用 `search()`——每次提问向量检索跑了两次。修复：`ask(question, docs)` 把搜索结果作为参数传入。

**改进方向：** 按固定字数切分（300 字 + 50 字重叠）；延迟加载 Embedding 模型；扫描版 PDF 加 OCR。

### Week 3 — AI Agent：学会"做事"

**核心链路（ReAct 循环）：**
```
用户: "特斯拉股价？"
  Step 1: LLM 收到问题 → 看工具列表 → 决定调 search_web("特斯拉股价")
  Step 2: 代码真正执行搜索（Tavily API）→ 返回结果
  Step 3: 结果喂回 LLM → 判断信息够了 → 组织语言回答
```

**自建 ReAct 循环（仅 30 行）：**
```python
for step in range(max_steps):
    response = client.chat.completions.create(
        model=..., messages=self.messages,
        tools=[t.to_openai_schema() for t in self.tools.values()]
    )
    msg = response.choices[0].message
    if not msg.tool_calls:
        return msg.content        # LLM 认为可以回答了
    for tc in msg.tool_calls:
        result = execute_tool(tc) # 你的代码真正执行
        self.messages.append({"role": "tool", "content": result})
```

**功能演进路径：**
```
v1: 1 个工具（假天气）→ 验证 ReAct 能跑
v2: 1 个真工具（Tavily 搜索）→ 真 API 打击
v3: 3 个工具（搜索 + 计算 + 真天气）→ 多工具自动选路
v4: 短期记忆 → 消息清理，多轮对话不混乱
v5: 长期记忆 → ChromaDB 跨对话持久化
v6: Planning → System Prompt 升级：列计划 → 执行 → 汇总
```

**最终能力：**

| 能力 | 实现方式 |
|------|---------|
| 5 个工具 | search_web（Tavily）、calculate（eval）、get_weather（Open-Meteo）、save_to_memory、search_memory |
| 短期记忆 | `run()` 结束时遍历 messages，只保留 system/user/clean assistant |
| 长期记忆 | ChromaDB + sentence-transformers，复用 Week 2 技术栈 |
| Planning | System Prompt 工程，零代码改动实现任务分解 |

**关键认知：** 自建 Agent 框架只需 30 行核心代码。LangChain 的 `AgentExecutor` 也是同样的 for 循环。先手写再学框架，理解深度完全不同。

**最深刻的 Bug：**
- LLM 假装调用了工具 → System Prompt 没硬约束"你必须调用"
- System Prompt 不够强硬 → 搜了 5 次还不回答，需要明确"什么时候该停"
- 短期记忆清理不彻底 → 下轮对话 LLM 看到 tool_calls 垃圾，行为异常

### Week 4 — LoRA 微调：学会"改模型"

**核心链路：**
```
1000 条 alpaca_zh_demo 数据
  → Qwen3.5-4B-Thinking（45 亿参数，冻结不动）
  → LoRA 插入低秩矩阵（只训练 1623 万参数 = 0.36%）
  → 66 分钟训练，378 步
  → loss 1.63 → 0.16
  → 模型身份从"Qwen 官方"变成"通用助手"
```

**训练数据：**
```
epoch 0.08: loss 1.6278    epoch 2.54: loss 0.5666    epoch 5.32: loss 0.1451
epoch 1.03: loss 1.3091    epoch 3.58: loss 0.3572    epoch 5.96: loss 0.1567 ← 最终
```

**学到的参数含义：**

| 参数 | 你设置的值 | 含义 |
|------|:--:|------|
| r | 8 | LoRA 矩阵宽度，只训练 0.36% 参数的秘密 |
| lora_alpha | 16 | 学到的知识的放大系数（一般设 r×2） |
| epoch | 6 | 全部数据过 6 遍。太少学不会，太多背答案 |
| learning rate | 5e-5 | 每一步调参的步长。cosine 衰减到接近 0 |
| loss | 1.63→0.16 | 模型"犯错"程度在持续下降 = 在学 |

**环境排障——实际最耗时的部分：**

| 问题 | 原因 | 解决 |
|------|------|------|
| libcudart.so.13 找不到 | 镜像 CUDA 12.8 vs torchaudio 需要 13 | 重装 torch |
| 系统盘 30G 爆满 | PyTorch 本体太大 | 扩容/清缓存/换镜像 |
| tokenizer 报 sentencepiece 缺失 | WebUI 和终端用不同 conda 环境 | 切换到正确环境的 pip |
| Qwen2.5-1.5B 下载后不可用 | 模型文件不完整 | 换镜像预装的 Qwen3.5-4B |

**LLaMA-Factory 帮你藏掉的东西：**
你在 WebUI 只设了 3 个值（模型、数据集、r=8）。它自动处理了：目标层选择（11 个注意力层）、优化器配置（AdamW + LoRA+）、batch size（2 + 梯度累积 = 16）、学习率调度（cosine）、checkpoint 保存（每 100 步）。

## 五、踩坑排行榜（按学习价值排序）

| 排名 | 坑 | 项目 | 现象 | 学到的最重要的事 |
|:--:|-----|:--:|------|------|
| 🥇 | **LLM 假装调用了工具** | Week 3 | LLM 回复"已保存！✅"但 save_to_memory 根本没被调用 | **LLM 会"表演"符合预期但实际没发生的回复。** 没有硬约束时它宁愿说"已完成"也不报错。解法：System Prompt 加"当用户说记住时，你必须调用 save_to_memory" |
| 🥈 | **System Prompt 不够强硬导致 Agent 无限循环** | Week 3 | Agent 搜了 5 次都不回答，每次都换关键词继续搜 | **Prompt 工程 = Agent 的边界控制。** 只在 Prompt 里写"搜几次"不够，需要明确规则"搜完 2-3 次后必须给出答案"。好的 Prompt = 告诉 LLM 什么时候该停 |
| 🥉 | **ChromaDB 旧数据污染新文档检索** | Week 2 | 上传了新文档但搜索还是返回之前那 4 条测试数据 | **持久化数据库的状态管理是隐式 bug 源。** 测试数据和真实数据混在一起时，错误不是报错而是"看起来对但实际错"。解法：加清空按钮 + 每次测试前重置 |
| 4 | **`ask()` 重复调用 `search()`** | Week 2 | 每次提问，向量检索跑了两次——app.py 调了一次，ask() 内部又调了一次 | **追踪数据流才能发现冗余。** 这种 bug 不会报错，只会让程序多浪费一倍的检索时间。看代码时追问"这一段谁调用、这一段又谁调用" |
| 5 | **DeepSeek 没有 Embedding API** | Week 2 | 以为直接用 `client.embeddings.create()` 就行，结果 404 | **做技术决策要查官方文档 + GitHub Issues，不靠"应该可以"的推测。** 最终确认 DeepSeek 只提供 Chat API，Embedding 用本地模型替代 |
| 6 | **DuckDuckGo 国内不稳定 → Tavily 字段名不匹配** | Week 3 | 换 API 后连续报 KeyError: `'href'` 和 `'body'` | **换 API 要逐字段检查数据格式。** 两个搜索 API 返回结构看起来像但字段名不同：`href` vs `url`, `body` vs `content`。每换一个外部依赖都要验证 |
| 7 | **Streamlit 执行模型导致按钮+上传组件冲突** | Week 2 | 点了"添加到知识库"按钮，文件没传进去，也没报错 | **用框架前要理解它的执行模型。** Streamlit 每次交互都重跑整个脚本——`st.button` 返回 True 的那次重跑时 `st.file_uploader` 已丢失。不用按钮，改自动触发 |
| 8 | **短期记忆清理不彻底导致下轮对话混乱** | Week 3 | 第二轮对话时 LLM 看到了上轮的 tool_calls 垃圾，行为异常 | **消息管理的粒度很重要。** 不只存 history，还要知道哪些该留（System/User/Clean Assistant）、哪些该删（tool_calls 中间状态）。`msg.model_dump()` 把 ChatCompletionMessage 转 dict 是基础 |

## 六、从 bug 到原则 —— 8 个坑提炼的工程原则

每个坑都不是孤立的。它们指向同一类问题。

| 原则 | 来源（坑） | 一句话 |
|------|------|------|
| **外部输入不可信** | LLM 假装调工具、DuckDuckGo 不稳定、Tavily 字段名不匹配 | 任何外部系统（API、LLM、用户输入）都可能返回你不期望的东西。永远加 try/except 和验证 |
| **状态管理是隐式 bug 源** | ChromaDB 旧数据污染、短期记忆清理不彻底 | 持久化数据和内存状态的"残留"不会报错，只会让行为悄悄变错。每次测试前清理状态 |
| **数据流比代码流更重要** | ask() 重复调用 search() | Bug 不只在"这行写错了"，还在"这个函数被不该调它的人调了"。画数据流图比读代码更能发现冗余 |
| **框架有执行模型，不理解就踩坑** | Streamlit 按钮+上传冲突、LLaMA-Factory conda 隔离 | 每个框架都有自己的"生命周期"。用之前花 10 分钟理解"它什么时候重跑我的代码" |
| **LLM 需要硬约束，软约束会被绕开** | Agent 无限循环、LLM 假装调工具 | "建议"和"规则"对 LLM 不够。用 `max_steps`、`required` 字段、明确指令来强制行为边界 |
| **API 能力不是"应该有的"，是"文档写了的"** | DeepSeek 没有 Embedding API | 调一个新 API 前先确认：1) 看文档确认有这个 endpoint 2) 看 Issues 确认没被废弃 3) 用最小请求测试 |

## 七、技术债务清单 —— 有意留下的不完美

好工程师知道什么该做，更好的工程师知道什么**暂时不做**。

| 债务 | 项目 | 为什么没修 | 什么时候修 |
|------|:--:|------|------|
| `eval()` 安全风险 | Week 3 | Agent 自己不会注入恶意代码，原型阶段够了 | 上线前替换为 `ast.literal_eval` |
| 文本切分太粗糙（`split("\n")`） | Week 2 | 核心链路验证优先，切分算法不是瓶颈 | 接入真实长文档时换 300 字 + 50 字重叠 |
| Embedding 模型每次 import 都加载 | Week 2 | 90MB 加载可接受，不挡核心流程 | 需要优化启动速度时改延迟加载 |
| 无流式输出（Agent） | Week 3 | Agent 调工具需要完整思考链，非流式更稳定 | 工具调用结果不流式、最终回答流式 |
| 消息历史无限增长 | Week 3 | 学习阶段对话不长，128K 窗口够用 | 加滑动窗口截断 |
| 未写单元测试 | 全部 | 原型阶段行为不确定，测试成本 > 收益 | 核心逻辑稳定后补 |
| 微调数据只有 1000 条 | Week 4 | 跑通流程比数据量重要 | 用 Agent 对话记录积累真实数据 |

## 九、技术直觉 —— 不需要思考就能做出的判断

经过四个项目，以下判断变成了肌肉记忆：

| 遇到的情况 | 直觉反应 |
|-----------|---------|
| API 返回 404 | 不是网络问题。先确认这个 endpoint 是否存在、模型名是否正确 |
| LLM 输出不对劲但没报错 | 检查 messages 历史里有没有 garbage（tool_calls 残留、重复的 system prompt） |
| 换了一个新的 API 服务 | 先打印返回的 JSON 结构，再写解析代码。字段名是不可信的 |
| import 报 ModuleNotFoundError | 先确认当前用的是哪个 Python/venv/conda 环境 |
| 程序"看起来在工作"但结果不对 | 追踪数据流——在每一步加 print，看数据在哪一步变味了 |
| 要选一个新技术栈 | 先查它"不能做什么"（Issues 里的 complaints），而不是"能做什么"（README 里的 features） |

## 十、学习方法的反思

### 有效的

| 方法 | 为什么有效 |
|------|-----------|
| **先跑通 20 行核心链路，再包装** | 出错时分得清是核心逻辑问题还是 UI/边缘问题 |
| **逐行写代码，逐行解释** | 不理解的东西不留在代码里 |
| **每个项目都写复盘文档** | 做完 ≠ 学会。写下来才发现哪里没真的理解 |
| **遇到 API 问题先去 GitHub Issues** | 官方文档可能过时，Issues 里是真实用户的真实问题 |
| **视频只看 15-20 分钟，然后立刻写代码** | 看 1 小时视频不如跑 10 分钟代码 |

### 可以改进的

| 当时的做法 | 应该的做法 |
|-----------|-----------|

## 七、面试叙述框架

### 30 秒总述

> "我暑假用一个月从零学了 AI 应用开发，做了四个递进的项目：从调用 LLM API，到构建 RAG 知识库，到自建 Agent 框架，到 LoRA 微调开源模型。全部基于 DeepSeek，代码都在 GitHub 上。"

### 纵深展开（面试官挑一个项目深挖时）

**Week 3 Agent 是最能打的项目：**

> "我自建了一个 ReAct Agent，没依赖 LangChain。核心就是 30 行 for 循环：LLM 决定调哪个工具 → 我的代码执行 → 结果回传 → 循环直到可以回答。5 个工具——搜索、计算、天气、记忆保存和搜索。短期记忆靠消息清理，长期记忆用 ChromaDB 跨对话持久化。Planning 通过 System Prompt 工程实现，没加额外代码。"

**追问"为什么不用 LangChain"：**
> "手写一遍才能理解底层。我现在看 LangChain 的 AgentExecutor 源码，知道它也是在跑一样的 for 循环。先理解原理再学框架，比先学框架再理解原理快。"

### 如果面试官关心"排障能力"

> "我踩过最有价值的坑是 LLM 假装调用了工具——它回复'已保存！✅'但实际什么都没做。后来我给 System Prompt 加了硬指令'当用户说记住时，必须调用工具'才解决。还有 ChromaDB 旧数据让新文档检索不准的问题——持久化数据库的状态管理是隐式 bug，不会报错，只会让你以为是模型不行。现在每加一个新功能，我先想'什么状态残留会影响它'。"

### 如果面试官问"你的项目有什么不足"

> "有意留了几项技术债务。比如 Agent 的 `calculate` 用 `eval()` 有安全风险，原型阶段够用；文本切分用了最简单的 `split('\n')`，因为核心链路才是瓶颈；没写单元测试，因为早期行为不稳定，写了也是重写。这些我都记录在项目复盘文档里了。"

## 十二、三个项目连起来 = 一个产品

```
用户: "帮我研究一下量子计算，整理成报告"

Agent (Week 3):
  🔧 search_web("量子计算 最新进展") → 3 篇文章
  🔧 save_to_memory("量子计算：...")  → 存长期记忆
  → 生成初步报告

RAG (Week 2):
  用户把报告和原文上传
  → ChromaDB 索引
  → 可以追问"这个结论出自哪篇文章？"

CLI/AI 助手 (Week 1):
  所有交互通过流式 API 调用 DeepSeek
  → 打字机效果、Token 统计、自动重试

微调 (Week 4):
  用积累的对话记录
  → 训练专属的"研究助手"模型
```

**这就是一个 AI 研究助手产品的完整技术栈。** 每个组件你都知道它内部怎么工作的——不是调别人的 API，是自己写的。
